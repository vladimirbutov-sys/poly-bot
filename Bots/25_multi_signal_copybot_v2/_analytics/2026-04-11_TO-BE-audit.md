### CRITICAL-1: Нет стоп-лосса для позиций 95-99c после удаления HP

**Приоритет:** CRITICAL  
**Затронутые изменения:** Изменение 2 (удаление HP) + Изменение 5 (удаление time-stop)

**Описание:**  
AS IS: позиции 95-99c имели HP стоп-лосс при bid <= 80c (`HP_STOP_LOSS_SELL_BELOW = 0.80`).  
TO BE: HP удалён, позиции 95-99c переходят на стандартный стоп-лосс = -65% от входа (`EXIT_STOP_LOSS_PCT = 0.65`).

Для позиции с входом 96c стандартный стоп-лосс сработает при:  
`96c * (1 - 0.65) = 33.6c`

Это означает потерю 65% вложенной суммы. HP стоп-лосс срабатывал при 80c — потеря ~17%. Разница катастрофическая: вместо потери $8.50 на ставке $50 (HP) бот потеряет до $35.75 на ставке $55 (новая система). Потери на одну позицию увеличиваются в 4+ раз.

Time-stop (16 дней, убыток <=12%) тоже убран — он бы хотя бы частично защитил, закрыв позицию через 16 дней с малым убытком.

**Пример сценария:**  
Denizz покупает по 96c на $800 (тиер $30). Бот входит по 96c. Рынок падает до 60c. HP стоп-лосс (80c) сработал бы — потеря $5. Новая система: стоп-лосс при 33.6c. Позиция зависает при 60c без стоп-лосса и без time-stop. Если Denizz не продаёт — позиция висит бесконечно при убытке 37.5%.

**Решение:**  
Добавить тиерованный стоп-лосс для высоких цен:

| Диапазон входа | Стоп-лосс при bid <= | Примерная потеря |
|---|---|---|
| 82-90c | 70c | ~15-20% |
| 90-95c | 80c | ~12-16% |
| 95-99c | 85c | ~11-14% |

Либо заменить процентный стоп-лосс абсолютным: если убыток >= X центов от входа, выходить.

### CRITICAL-2: "Зависшая позиция" — ни один exit-механизм не срабатывает

**Приоритет:** CRITICAL  
**Затронутые изменения:** Изменение 4 (follow-sell) + Изменение 5 (time-stop) + Изменение 2 (HP)

**Описание:**  
В TO BE при sell_ratio < 60% И нашем PnL < 0 follow-sell НЕ срабатывает. Time-stop убран. Стандартный стоп-лосс (65%) для дорогих позиций крайне далеко.

Пример: Denizz продал 50% позиции. Мы в убытке (bid = 90c при входе 96c). Что происходит?
- Follow-sell: sell_ratio 50% в бакете 30-60%. PnL < 0 → **НЕ ВЫХОДИМ**
- Time-stop: **УДАЛЁН**
- Стоп-лосс: 96c * 0.35 = 33.6c. Bid = 90c → не срабатывает
- HP стоп-лосс: **УДАЛЁН**

Позиция зависает навсегда. Единственные выходы: Denizz продаёт >60%, цена падает до 33.6c, или рынок разрешается.

Это ещё хуже для средних цен. Вход по 70c, bid = 65c (убыток ~7%). Denizz продал 40%. Follow-sell: PnL < 0, sell_ratio < 60% → НЕ ВЫХОДИМ. Time-stop: УДАЛЁН. Стоп-лосс: 70c * 0.35 = 24.5c — далеко. Капитал заморожен.

**Решение:**  
Как минимум одно из:
1. Не удалять time-stop полностью — сделать его длиннее (30-45 дней вместо 16), но оставить как последний рубеж защиты
2. При follow-sell добавить правило: если sell_ratio >= 30% И PnL < 0 И прошло > 7 дней — выходить (Denizz давно начал сворачивать)
3. Ужесточить стоп-лосс для дорогих позиций (см. CRITICAL-1)

### CRITICAL-3: Удаление PRICE_BET_MULTIPLIERS увеличивает ставки в зоне 82-98c в 2.5-3.3 раза

**Приоритет:** CRITICAL  
**Затронутые изменения:** Изменение 2 (удаление PRICE_BET_MULTIPLIERS)

**Описание:**  
AS IS: ставка при 93c = $200 * 0.3 = **$60** (множитель 0.3 для 90-98c).  
TO BE: ставка при 93c = $200 * 1.0 = **$200** (множитель убран, горизонт = 1.0 если end_date < 30 дней).

Это увеличение в 3.3 раза на позицию. В зоне 82-90c: было $200 * 0.4 = $80, стало $200. Увеличение в 2.5 раза.

Документ TO BE говорит "нет больше ценового множителя (то есть множитель = 1.0 для всех цен)", но при этом не объясняет, почему допустимо ставить $200 по цене 95c, где upside (потенциал роста) всего 5 центов = $10.5 максимальной прибыли на $200 (5.25% ROI при win).

Только горизонт частично компенсирует: при 90+ днях множитель 0.4, что даёт $80 — близко к старым $60. Но при коротком горизонте (0-30 дней, множитель 1.0) ставка будет $200 — в 3.3 раза больше старой.

**Решение:**  
Ввести ценовой множитель для зоны 82-99c, пусть и менее агрессивный чем AS IS:

| Диапазон | Предлагаемый множитель | Было AS IS |
|---|---|---|
| 82-90c | 0.6 | 0.4 |
| 90-95c | 0.5 | 0.3 |
| 95-99c | 0.4 | 0.3 |

Или сделать отдельные тиеры ставок для высоких цен.

### WARNING-1: Граничное значение end_date = ровно 30 дней — неопределённость

**Приоритет:** WARNING  
**Затронутое изменение:** Изменение 3 (горизонт)

**Описание:**  
Таблица в TO BE определяет диапазоны так:
- 0-30 дней → множитель 1.0
- 30-60 дней → множитель 0.8

Если end_date = ровно 30 дней от момента ставки — какой множитель? 1.0 или 0.8?

В коде это определится конструкцией `if days <= 30: ... elif days <= 60:`, но TO BE не уточняет. При обычном `[0, 30)` и `[30, 60)` значение 30 попадёт в 0.8. При `[0, 30]` и `(30, 60]` — в 1.0. Разница: $200 → $200 или $200 → $160.

**Решение:**  
Явно указать в спецификации, используются включительные или исключительные границы. Рекомендация: `< 30` → 1.0, `>= 30 and < 60` → 0.8 (левая граница включена, правая исключена), как сделано в MAX_SLIPPAGE_TIERS.

### WARNING-4: Двухступенчатый вход — частичное исполнение лимитки не описано

**Приоритет:** WARNING  
**Затронутое изменение:** Изменение 6 (двухступенчатый вход)

**Описание:**

Но не описан четвёртый вариант: **PARTIAL** (частичное исполнение за 30 минут). Что делать, если за 30 минут исполнилось 40% лимитки?

Добавить в спецификацию:
- При PARTIAL после 30 минут: сохранить исполненную часть как позицию, отменить остаток
- Определить минимальный fill: если исполнено < $5 → отменить полностью (не стоит открывать мелкую позицию)

### WARNING-5: Двухступенчатый вход — буфер может запустить второй сигнал во время ожидания

**Приоритет:** WARNING  
**Затронутое изменение:** Изменение 6 (двухступенчатый вход)

**Описание:**  
Лимитный ордер ступени 2 ждёт до 30 минут. За это время:
1. Denizz продолжает покупать тот же рынок
2. Буфер накапливает новые покупки
3. `buf_key` уже в `_signaled_keys`, поэтому новые покупки идут по пути **tier upgrade**
4. Бот может запустить `execute_part1()` для upgrade, пока лимитный ордер ступени 2 ещё висит

Результат: два параллельных ордера на покупку. Если оба исполнятся — позиция будет больше запланированной.

**Решение:**  
Добавить флаг `pending_limit_order` в буфер. Блокировать tier upgrade пока лимитка активна. После исполнения/отмены/таймаута — снять блокировку.

### WARNING-6: Dedup (60 сек) и лимитный ордер на 30 минут — конфликт

**Приоритет:** WARNING  
**Затронутое изменение:** Изменение 6 (двухступенчатый вход) + текущий dedup

**Вывод:** Этот конфликт не критичен. Текущая архитектура буфера + signaled_keys уже защищает от дублирования входов.

### WARNING-7: On-chain sync увеличивает позицию, затем Denizz продаёт — бот пытается продать увеличенную сумму

**Приоритет:** WARNING  
**Затронутое изменение:** Изменение 7 (on-chain sync)

**Описание:**  
Сценарий:
1. Трекер: 100 акций. On-chain: 150 акций (кто-то вручную купил 50).
2. `sync_with_onchain()` увеличивает трекер до 150 акций.
3. Denizz продаёт 70% → бот пытается продать 150 * 100% = 150 акций.
4. Продажа проходит, потому что on-chain у нас действительно 150 акций.

Это **корректное поведение** — если on-chain у нас 150 акций, мы должны продать все 150. Проблемы нет, если sync правильно обновил cost_usd и avg_entry.

Но есть нюанс: `cost_usd` дополнительных акций оценивается по `avg_entry` существующей позиции, а не по реальной цене покупки. Если ручная покупка была по другой цене — PnL будет искажён. Это уже описано в Изменении 7 как ограничение ("оценка по avg_entry").

**Решение:**  
Добавить в лог уведомление: "Sync adjusted position UP by X shares — PnL may be inaccurate". Принять как допустимое ограничение.

### WARNING-9: Slippage тир 95-96c: 0.75c — математическая проверка

**Приоритет:** WARNING  
**Затронутое изменение:** Изменение 1 (slippage)

**Описание:**  
Вопрос: при ask 96.5c и entry 95.8c, slippage = 0.7c. Тир 95-96c, макс = 0.75c.

Проверка: `0.7 > 0.75 + 0.0005`? → `0.7 > 0.7505`? → **Нет**. Ордер **проходит**. Корректно.

Но `entry_price` = 95.8c (цена Denizz, не current_ask). Тир определяется по `entry_price`, а не по `current_ask`:
```python
def get_max_slippage(price: float) -> float:
    for min_p, max_p, max_slip in MAX_SLIPPAGE_TIERS:
        if min_p <= price < max_p:
            return max_slip
```

95.8c попадает в тир 95-96c (0.95 <= 0.958 < 0.96). Макс slippage = 0.75c = 0.0075.
Slippage = 96.5c - 95.8c = 0.7c = 0.007.
`0.007 > 0.0075 + 0.0005`? → `0.007 > 0.0080`? → **Нет**. Проходит. Корректно.

**Вывод:** Математика верна.

### WARNING-10: Допуск float +0.0005 и граничный случай

**Приоритет:** WARNING  
**Затронутое изменение:** Изменение 1 (slippage)

**Описание:**  
Вопрос: slippage ровно = max + 0.0005 — заблокировано или нет?

Проверка: `slippage > max_slip + 0.0005`. Если slippage = max_slip + 0.0005 → `max_slip + 0.0005 > max_slip + 0.0005` → **False**. Не заблокировано.

Это значит, что реальный допуск = max_slip + 0.0005 включительно. Для тира с макс 0.75c: реальный предел = 0.7505c. Допустимо — это решает проблему float-округления без значимого расширения.

### WARNING-11: Rule C (whipsaw) и новый follow-sell с частичными выходами

**Приоритет:** WARNING  
**Затронутые изменения:** Изменение 4 (follow-sell) + текущий Rule C

**Описание:**  
В TO BE follow-sell может продать 25% позиции (sell_ratio 10-30%, PnL > 0). Это записывается в трекер как `record_sell()` с каким-то `reason`.

Вопрос: если после частичной продажи 25% позиция остаётся "open" (size_shares > 0.1), а затем Denizz покупает снова — будет ли Rule C блокировать?

Ответ: **Нет**, Rule C не заблокирует, потому что:
1. Позиция всё ещё open → `buf_key` остаётся в `_signaled_keys`
2. Новые покупки Denizz идут по пути tier upgrade, не по пути нового входа
3. Rule C проверяется только для **новых** входов (не tier upgrade)

Однако если follow-sell продал 100% (позиция закрылась) → Rule C МОЖЕТ заблокировать повторный вход в течение 12 часов при изменении цены < 5%. Это **корректное поведение** — мы не хотим повторно входить по той же цене сразу после выхода.

**Вывод:** Конфликта нет. Rule C работает корректно с новым follow-sell.
