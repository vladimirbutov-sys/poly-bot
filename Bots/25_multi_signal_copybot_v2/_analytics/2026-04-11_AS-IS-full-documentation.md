## 1. Мониторинг

**Файл:** `monitor.py`
**Функция:** `poll_loop()` / `_poll_player()`

### Что делает

Запускает **один поток опроса на каждого игрока** (сейчас только denizz). Каждый поток обнаруживает события BUY, SELL и MERGE через два параллельных канала:

1. **Activity API** (`DATA_API/activity`) -- опрашивается каждый цикл (каждые `POLL_INTERVAL` = **5 секунд**), получает последние 20 сделок
2. **Сравнение снимков позиций** (`DATA_API/positions`) -- запускается каждый **5-й цикл** (= каждые 25 секунд), сравнивает предыдущий снимок с текущим

### Активный игрок

| Игрок | Кошелёк | Статус |
|--------|--------|--------|
| denizz | `0xbaa2bcb5439e985ce4ccf815b4700027d1b92c73` | ACTIVE |
| Car | удалён 2026-04-09 | DISABLED |
| aenews2 | удалён 2026-04-09 | DISABLED |

**Причина удаления:** Инцидент с Ираном 7 апреля -- merge-арбитражные сделки Car были ошибочно прочитаны как реальные направленные сигналы, что вызвало каскадные продажи позиций denizz.

### Обнаружение через Activity API

Для каждой новой сделки (дедупликация по `{tx_hash}_{conditionId}_{timestamp}`):
- Игнорируются сделки с `timestamp < start_time` (unix-время запуска бота)
- **BUY**: `type == "TRADE"` и `side == "BUY"` и `size > 0` --> вызывает `on_buy(player, event)`
- **SELL**: `type == "TRADE"` и (`side == "SELL"` или `size < 0`) --> вызывает `on_sell(player, event)`
- **MERGE**: `type == "MERGE"` --> вызывает `on_merge(player, event)` с `reason = "MERGE_EXIT"`
- **SPLIT**: логируется, но без обратного вызова

### Обнаружение через сравнение снимков (каждый 5-й цикл)

Сравнивает `build_snapshot()` предыдущих и текущих позиций:
- **Позиция исчезла** (prev существовала, curr = None, prev size > 0.1):
  - Проверка в блокчейне через `CTF.balanceOf` перед срабатыванием продажи
  - Если баланс в блокчейне > 5% от prev size --> **ФАНТОМНАЯ ПРОДАЖА заблокирована** (баг пагинации API)
  - Если RPC не ответил --> **защитная мера: пропустить** (НЕ запускать продажу)
  - Если баланс в блокчейне около нуля --> подтверждённый реальный выход, запускается `on_sell`
- **Размер уменьшился** (curr < prev - 0.5):
  - Проверка в блокчейне: если баланс > 95% от prev size --> **ФАНТОМНОЕ УМЕНЬШЕНИЕ заблокировано**
  - Если RPC не ответил --> пропустить (защитная мера)
  - Если подтверждено: `actual_sold = prev_size - onchain_balance`, запускается `on_sell` если actual_sold >= 0.5

### Восстановление при запуске

При старте потока сканируются последние 100 сделок activity на предмет продаж, которые произошли ПОСЛЕ открытия наших позиций. Если найдены, запускается `on_sell()` для компенсации пропущенных продаж во время простоя бота. Обрабатываются только продажи для позиций, открытых ЭТИМ игроком (проверяется совпадение `signal_player` и сравниваются временные метки).

### Ключевые параметры

| Параметр | Значение | Источник |
|-----------|-------|--------|
| POLL_INTERVAL | 5 секунд | config.py |
| Лимит запроса Activity | 20 за цикл | monitor.py |
| Частота проверки снимков | Каждый 5-й цикл (25с) | monitor.py |
| Размер страницы позиций | 100 на страницу, с пагинацией | monitor.py |
| Порог фантомной продажи | блокчейн > 5% от prev size | monitor.py |
| Порог фантомного уменьшения | блокчейн > 95% от prev size | monitor.py |
| Задержка между потоками | 1 секунда между запусками потоков | monitor.py |

## 2. Буферизация

**Файл:** `main.py` -- `handle_buy()`, `_get_buf()`, `_prune_buffer()`
**Хранилище:** `buy_buffers.json` (сохраняется на диск при каждом вызове `handle_buy`)

### Что делает

Накапливает отдельные события покупки от каждого игрока, пока общая сумма в USD не пересечёт минимальный порог. Это нужно потому, что denizz часто набирает позиции множеством мелких покупок на протяжении нескольких часов, и боту нужно распознать, когда общий объём вложений достигнет порога сигнала.

### Структура буфера

```
_buy_buffers = {
    "denizz": {
        "{conditionId}_{tokenId}": {
            "buys": [[timestamp, cost_usd], ...],
            "total_usd": float,
            "notified": bool,
            "first_price": float,
            "last_tier_bet": float
        }
    }
}
```

### Окно буфера

| Параметр | Значение | Описание |
|-----------|-------|-------------|
| BUFFER_WINDOW | 86400 (24ч) | Покупки старше этого срока удаляются из буфера |

**Логика очистки** (`_prune_buffer`): При каждом обращении удаляются покупки с `timestamp < now - 86400`, затем пересчитывается `total_usd` из оставшихся покупок.

### Порог сигнала

| Игрок | MIN_PLAYER_INVESTED | Описание |
|--------|-------------------|-------------|
| denizz | $500 | Минимальная накопленная сумма в USD для признания сигнала |

### Последовательность действий

1. Каждое событие покупки добавляет `[time.time(), cost_usd]` в буфер
2. Буфер очищается (окно 24ч)
3. `total_usd` пересчитывается из оставшихся покупок
4. Если `total_usd >= 500` и `notified == False`: отправляется уведомление в Telegram, устанавливается `notified = True`
5. Если `total_usd < MIN_PLAYER_INVESTED` ($500): буферизация и ожидание, выводится "Buffering buy #N"
6. Если `total_usd >= 500`: переход к проверке сигнала / HP-переопределению / повышению уровня

### Ключи сигналов

`_signaled_keys` = `{player: set(buf_key)}` -- отслеживает, какие пары (cid, token) уже получили сигнал. После срабатывания сигнала `buf_key` добавляется в этот набор. Последующие покупки на том же рынке идут по пути **повышения уровня** вместо нового входа.

### Восстановление из трекера

`_rehydrate_from_tracker()` запускается:
- При старте
- Каждые ~5 минут (из `periodic_checks`)

Два направления:
1. **ДОБАВЛЕНИЕ** signaled_keys для позиций, открытых в трекере (чтобы повышение уровня работало после перезапуска)
2. **УДАЛЕНИЕ** устаревших signaled_keys для позиций, которые больше не открыты (проданы/выиграны/проиграны) -- чтобы бот мог повторно войти в рынок, если игрок входит снова после нашего выхода

### Сохранение на диск

Буфер + ключи сигналов сохраняются атомарно в `buy_buffers.json` (запись в `.tmp`, затем `os.replace`) при каждом вызове `handle_buy` через `_save_buffers()`. Загружаются при запуске через `_load_buffers()`.

## 4. Размер ставки

**Файл:** `filters.py` -- `calculate_bet_size()`
**Файл:** `config.py` -- `PLAYER_BET_TIERS`, `PRICE_BET_MULTIPLIERS`, `BET_SCALE`

### Формула

```
bet = (сумма подходящих приращений по уровням) * price_multiplier * BET_SCALE
```

### Шаг 1: Уровни по объёму вложений (суммируются)

Уровни Denizz:

| Вложения игрока >= | Добавленное приращение | Максимум нарастающим итогом |
|-------------------|----------------|----------------|
| $500 | +$30 | $30 |
| $2,000 | +$25 | $55 |
| $5,000 | +$50 | $105 |
| $10,000 | +$95 | $200 |

Каждый уровень суммируется: если denizz вложил $12,000, срабатывают ВСЕ четыре уровня = $200.

### Шаг 2: Множитель цены

| Диапазон цен | Множитель | Обоснование |
|-------------|-----------|-----------|
| 0.00 - 0.15 | 0.7 | Дёшево, низкая ликвидность |
| 0.15 - 0.50 | 1.0 | Оптимальная зона, лучший ROI |
| 0.50 - 0.70 | 0.9 | Нейтрально, небольшое снижение |
| 0.70 - 0.82 | 0.8 | Дорого, низкий потенциал роста |
| 0.82 - 0.90 | 0.4 | Очень дорого, бэктест отрицательный |
| 0.90 - 0.98 | 0.3 | Почти наверняка, минимальный потенциал |

### Шаг 3: Масштаб по режиму

| Режим | BET_SCALE |
|------|-----------|
| test | 0.5 |
| live | 1.0 |

Сейчас в режиме LIVE, поэтому BET_SCALE = 1.0.

### Шаг 4: Правило A+ (штраф за поздний вход)

`calculate_entry_size_multiplier(player_avg, current_ask)`:
- `mult = current_ask / player_avg`

| Соотношение mult | Множитель размера | Метка |
|-----------|----------------|-------|
| <= 1.2x | 1.0 | on-time |
| 1.2 - 1.5x | 0.75 | late |
| 1.5 - 2.0x | 0.50 | bad |
| 2.0 - 3.0x | 0.25 | terrible |
| > 3.0x | 0.10 | extreme |

### Шаг 5: Штраф за долгосрочный горизонт

Рынки с `end_date >= 2026-12-01` умножаются на `LONG_HORIZON_MULTIPLIER = 0.2` (20%). Причина: долгосрочные политические позиции denizz показали риск концентрации.

### Пример расчёта

Denizz вкладывает $6,000 в рынок по 0.30c (наш ask = 0.32c, средняя цена игрока = 0.28c):
1. Уровни: $500 -> +$30, $2000 -> +$25, $5000 -> +$50 = **$105**
2. Множитель цены (0.32 в диапазоне 0.15-0.50): **1.0**
3. BET_SCALE (live): **1.0**
4. Правило A+ (0.32/0.28 = 1.14x <= 1.2): **1.0**
5. Долгосрочный горизонт: Н/П = **1.0**

Итоговая ставка = $105 * 1.0 * 1.0 * 1.0 * 1.0 = **$105**

### Метки уровней (только для отображения/логирования)

| Вложения игрока | Метка уровня |
|----------------|------------|
| < $2,000 | B |
| $2,000 - $4,999 | A |
| $5,000 - $9,999 | S |
| >= $10,000 | S+ |

### Логика повышения уровня (main.py)

Когда игрок добавляет ещё в существующую позицию (buf_key уже отмечен как сигнал):
1. Получить реальный объём вложений из API: `effective_invested = max(buffer, api)`
2. **Правило B**: если `our_entry_price / player's_current_buy_price > 1.5` --> ЗАБЛОКИРОВАНО (мы заплатили бы на 50%+ больше, чем игрок платит сейчас)
3. Рассчитать новый размер ставки из effective_invested
4. `increment = new_bet - already_bet` (то, что уже размещено)
5. Применить Правило A+ к ПРИРАЩЕНИЮ (не к общей сумме)
6. Применить множитель долгосрочного горизонта к приращению
7. Если increment >= MIN_BET_USD ($10): исполнить через `entry_manager.execute_part1` в новом потоке
8. Обновить `last_tier_bet = already_bet + increment` (отслеживает фактически потраченное, не до масштабирования)

HP-позиции НИКОГДА не повышаются в уровне (проверка добавлена 2026-04-09).

### Минимальная ставка и резерв

| Параметр | Test | Live |
|-----------|------|------|
| MIN_BET_USD | $3 | $10 |
| RESERVE_USD | $15 | $150 |

Ставка ограничивается доступным балансом. Если после ограничения она падает ниже MIN_BET_USD, вход пропускается.

## 5. Исполнение ордеров

**Файл:** `executor.py`
**Файл:** `entry_manager.py` -- `execute_part1()`

### Процесс покупки

1. Получить текущий лучший ask из стакана (`filters.get_orderbook_prices`)
2. Использовать лучший ask как лимитную цену (запасной вариант: цена входа игрока)
3. Рассчитать количество акций: `size_usd / price`, минимум `MIN_SHARES = 5`, округление вверх до 2 знаков
4. Отправить GTC (Good Till Cancel) лимитный ордер через Polymarket CLOB API (`py_clob_client`)
5. Записать позицию в трекер немедленно
6. Ожидать исполнения (см. ниже)

### Ожидание исполнения

`wait_for_fill_with_details(order_id, timeout=ORDER_TTL_SECONDS)`:
- **ORDER_TTL_SECONDS = 600** (10 минут)
- Опрашивает статус ордера каждые **10 секунд**
- Возможные исходы:

| Статус | Действие |
|--------|--------|
| MATCHED | Исполнение подтверждено. Уведомление через Telegram. |
| PARTIAL | Часть акций исполнена. Сохранить исполненную часть, вернуть остаток в баланс. Обновить трекер с фактическими акциями/стоимостью. |
| CANCELLED | Ордер был отменён извне. |
| TIMEOUT | Истёк TTL. Отменить оставшуюся часть. Если filled_pct > 0.5% --> обработать как PARTIAL. |

### Обработка частичного исполнения (покупка)

При PARTIAL:
- `actual_cost = size_matched * order_price`
- Возврат: `pos["cost_usd"] - actual_cost` добавляется обратно в `current_balance`
- Трекер обновляется с фактическими `size_shares` и `cost_usd`
- `_partial_fill_note` добавляется в запись позиции

При TIMEOUT/NO FILL:
- Запись позиции удаляется из трекера
- `cost_usd` возвращается в `current_balance`
- `total_bets` уменьшается на 1

### Процесс продажи

1. Отправить GTC лимитную продажу по лучшему bid
2. Ожидать исполнения (таймаут = **300 секунд** для ордеров продажи в `_execute_sell`)
3. При MATCHED: записать продажу в трекер
4. При PARTIAL (matched > 0.5 акций): записать частичное исполнение, повторить попытку для остатка по **price * 0.98** (на 2% ниже)
5. При TIMEOUT: повторить попытку для полной суммы по **price * 0.98**
6. Повторная попытка также ждёт 300с, обрабатывает результаты MATCHED/PARTIAL

### Трёхчастный вход (сейчас отключён)

**Значения конфигурации (фактически одночастный):**

| Параметр | Значение | Эффект |
|-----------|-------|--------|
| ENTRY_PART1_PCT | 1.00 (100%) | Полная ставка сразу |
| ENTRY_PART2_PCT | 0.00 (0%) | Отключено |
| ENTRY_PART3_PCT | 0.00 (0%) | Отключено |
| ENTRY_PART2_DELAY_H | 2ч | Когда сработала бы часть 2 |
| ENTRY_PART2_MAX_DELAY_H | 4ч | Когда часть 2 истекает |
| ENTRY_PART2_MAX_RISE | 0.15 (15%) | Пропустить часть 2 если цена выросла >15% |
| ENTRY_PART3_DIP_PCT | 0.10 (10%) | Часть 3 срабатывает при просадке 10%+ от части 1 |
| ENTRY_PART3_EXPIRY_DAYS | 7 | Часть 3 истекает через 7 дней |

Трёхчастное разделение было отключено после того, как моделирование не показало пользы на быстро закрывающихся сделках. Все входы теперь на 100% мгновенные (только часть 1).

`check_pending_parts()` всё ещё запускается периодически, но с 0% для частей 2/3 фактически ничего не делает.

## 6. HP-стратегия (переопределение по высокой цене)

**Файл:** `filters.py` -- `check_high_price_override()`
**Файл:** `entry_manager.py` -- `execute_hp_bet()`
**Файл:** `config.py` -- HP_* константы

### Что делает

Отдельный путь входа для рынков, где игрок покупает по очень высоким ценам (95-99c) на рынках с близким разрешением. Обходит стандартные фильтры категорий/оппозиции. Использует фиксированный размер ставки с собственным стоп-лоссом.

### Условия срабатывания

ВСЕ должны быть истинными:

| Условие | Параметр | Значение |
|-----------|-----------|-------|
| HP включён | HP_ENABLED | True |
| Цена игрока >= мин | HP_MIN_PRICE | 0.95 |
| Цена игрока < без-ставки | HP_NO_BET_PRICE | 0.99 |
| Информация о рынке доступна | -- | Gamma API возвращает данные |
| Дата окончания в пределах окна | HP_MAX_END_DATE_DAYS | 90 дней |
| Дата окончания не в прошлом | -- | days_ahead >= 0 |
| Проскальзывание в пределах уровня | HP_SLIPPAGE_TIERS | см. таблицу |
| Текущий ask < без-ставки | HP_NO_BET_PRICE | 0.99 |

### HP-уровни проскальзывания

| Диапазон цены игрока | Макс. проскальзывание |
|-------------------|-------------|
| 0.95 - 0.97 | 0.5c (0.005) |
| 0.97 - 0.99 | 0.2c (0.002) |

Проскальзывание = `current_ask - player_price`.

### HP-размер ставки

**Фиксированный: HP_BET_USD = $50.00** (ограничивается доступным балансом, минимум $5)

### HP-исполнение ордера

1. Лимитная цена = `min(max_ask, current_ask)`, где `max_ask = min(player_price + max_slip, HP_NO_BET_PRICE - 0.001)`
2. Если лимитная цена >= HP_NO_BET_PRICE (0.99) --> пропустить
3. Покупка одной частью (без частей 2/3)
4. Записывается с `tier = "HP"`, `strategy = "HP"`
5. Ожидание исполнения с той же обработкой PARTIAL, как для стандартных ордеров

### Что HP НЕ проверяет

- Фильтр категорий (пропускается)
- Проверка оппозиции (пропускается)
- Правило A+ штраф за поздний вход (пропускается)
- Штраф за долгосрочный горизонт (пропускается)
- Исключённые ключевые слова (пропускаются)

### Правила выхода HP (см. раздел 10)

HP-позиции имеют полностью отдельную логику выхода.

## 7. Выход: следование за продажей

**Файл:** `exit_manager.py` -- `handle_player_sell()`
**Файл:** `main.py` -- `handle_sell()`, `handle_merge()`

### Архитектура (переписана 2026-04-10)

Монитор -- это только **подсказка**. ВСЕ решения о продаже основаны на **истинных данных блокчейна** через `CTF.balanceOf`.

### Последовательность

1. **Защита от дублирования** (окно 60с): пропустить, если тот же `(player, cid, token)` сработал <60с назад. Merge-события обходят дедупликацию.
2. **Данные блокчейна**: прочитать текущий баланс игрока через `CTF.balanceOf` RPC
3. **Сравнение с кэшем**: `actual_sold = cached_size - current_onchain`
4. **Проверка на фантом**: если `actual_sold <= 0` --> ФАНТОМ (позиция не уменьшилась), ПРОПУСТИТЬ
5. Если RPC не ответил --> **защитная мера: НЕ продавать**
6. Если нет базового значения в кэше --> сохранить текущее и пропустить (первый раз видим этот токен)
7. **Обновить кэш** немедленно свежим значением
8. `sold_pct_player = actual_sold / cached_size`
9. **Найти нашу соответствующую позицию**: тот же (condition_id, token_id), status=open
10. **Проверка игрока-источника сигнала**: выходить только если ЭТОТ игрок открыл нашу позицию (совпадение `signal_player`)

### Матрица решений

| Условие | Действие | Правило |
|-----------|--------|------|
| Source = "merge" | Полный выход | Merge -> немедленная полная продажа |
| sold_pct неизвестен | Полный выход | По умолчанию: предполагаем полный выход |
| sold_pct < 10% | **ПРОПУСТИТЬ** (пыль) | `PLAYER_SELL_DUST_PCT = 0.10` |
| sold_pct >= 70% | Полный выход | `PLAYER_EXIT_SELL_PCT_THRESHOLD = 0.70` (Правило 3) |
| 10-70%, игрок в УБЫТКЕ | Зеркалить % нашей позиции | Правило 2a |
| 10-70%, игрок в ПРИБЫЛИ, МЫ в прибыли | Зеркалить % | Правило 2b |
| 10-70%, игрок в ПРИБЫЛИ, МЫ в убытке | **ПРОПУСТИТЬ** (не фиксировать наш убыток) | -- |
| 10-70%, P&L игрока неизвестен, МЫ в прибыли | Зеркалить % | -- |
| 10-70%, P&L игрока неизвестен, МЫ в убытке | **ПРОПУСТИТЬ** | -- |

### Определение прибыли/убытка игрока

Используется `get_player_cost_basis()`:
1. **Основной**: data-api `/positions` -> `avgPrice` (средневзвешенная цена оставшихся акций)
2. **Запасной** (полный выход): FIFO-реконструкция из истории сделок `/activity`

`PROFIT_DELTA = 0.01` -- игрок/мы считаемся "в прибыли" если sell_price > avg * 1.01.

### Проверка разрыва цен

Если source != "merge" И player_sell_price известна И мы НЕ в прибыли:
- Если `(player_sell_price - our_sell_price) / player_sell_price > 0.40` --> ПРОПУСТИТЬ (наша цена на >40% хуже, чем у игрока)

### Кэш размера позиции игрока

| Настройка | Значение |
|---------|-------|
| `_player_size_cache` | `{(player, cid, token): {"size": float, "ts": int}}` |
| Инициализация при запуске | `init_player_cache()` из data-api, все позиции с size > 0 |
| Обновление | `refresh_cache_for_open_positions()` каждые ~60с, только токены где У НАС есть открытые позиции |
| Метод | Прямой вызов `CTF.balanceOf` RPC для каждого токена |

## 8. Выход: стоп-лосс

**Файл:** `exit_manager.py` -- `check_exits()`, EXIT 2

### Когда срабатывает

Запускается на каждом цикле `periodic_checks` (каждые `POSITIONS_CHECK_INTERVAL = 60` секунд).

Для каждой не-HP открытой позиции:
```
drop_pct = (entry_price - best_bid) / entry_price
if drop_pct >= EXIT_STOP_LOSS_PCT:  # 0.65 = 65%
    --> SELL
```

| Параметр | Значение |
|-----------|-------|
| EXIT_STOP_LOSS_PCT | 0.65 (падение на 65% от входа) |

**Пример:** Вход по 0.50, лучший bid падает до 0.175 --> падение = 65% --> стоп-лосс срабатывает.

Продаёт по текущему `best_bid`. Если продажа не исполнилась, повторяет по `price * 0.98`.

## 9. Выход: тайм-стоп

**Файл:** `exit_manager.py` -- `check_exits()`, EXIT 3

### Когда срабатывает

Для каждой не-HP открытой позиции:
```
days_held = (now - open_timestamp) / 86400
if days_held >= EXIT_TIME_STOP_DAYS:  # 16 days
    loss_pct = (entry - best_bid) / entry
    if loss_pct <= EXIT_TIME_STOP_MAX_LOSS:  # 0.12 = 12%
        --> SELL (close the position)
    else:
        --> HOLD (loss too large, don't sell at big loss)
```

| Параметр | Значение |
|-----------|-------|
| EXIT_TIME_STOP_DAYS | 16 дней |
| EXIT_TIME_STOP_MAX_LOSS | 0.12 (12%) |

Логика: Через 16 дней закрыть позицию, ЕСЛИ убыток небольшой (<=12%) или мы в прибыли. Если убыток превышает 12%, продолжаем удерживать (не продавать с большим убытком, дать рынку разрешиться или восстановиться).

## 10. Выход: HP

**Файл:** `exit_manager.py` -- `check_exits()`, секция HP

### Правила для HP-позиций

HP-позиции (`tier == "HP"` или `strategy == "HP"`) имеют полностью отдельную логику выхода:

| Правило | Условие | Действие |
|------|-----------|--------|
| Удержание до разрешения | Всегда | Нет тейк-профита по 0.99 (стандартная целевая цена пропускается) |
| HP стоп-лосс | `best_bid <= 0.80` | Продажа по `max(0.01, best_bid - 0.05)` |
| Нет тайм-стопа | Всегда | Пропускается (хотим погасить по $1 при разрешении) |
| Нет стандартного стоп-лосса | Всегда | Стоп-лосс 65% НЕ применяется |

### Параметры HP стоп-лосса

| Параметр | Значение |
|-----------|-------|
| HP_STOP_LOSS_SELL_BELOW | 0.80 |
| HP_STOP_LOSS_SLIPPAGE | 0.05 (5c) |

**Пример:** HP-позиция открыта по 0.96, цена падает до 0.79 --> стоп-лосс срабатывает, продажа по `max(0.01, 0.79 - 0.05) = 0.74`.

### Целевая цена для стандартных позиций

| Параметр | Значение | Условие |
|-----------|-------|-----------|
| EXIT_SELL_AT_PRICE | 0.99 | Только если `best_bid > entry` (прибыльно) |

Стандартные позиции продаются по 0.99, если прибыльны. HP-позиции удерживаются до разрешения рынка.

### Структура данных

```json
{
    "positions": {
        "<order_id>": {
            "condition_id": "...",
            "token_id": "...",
            "title": "...",
            "outcome": "Yes/No",
            "event_slug": "...",
            "entry_price": 0.5,
            "avg_entry": 0.5,
            "size_shares": 100.0,
            "cost_usd": 50.0,
            "tier": "B/A/S/S+/HP/upgrade",
            "strategy": "standard/HP",
            "signal_player": "denizz",
            "parts_filled": 1,
            "parts_planned": 1,
            "order_ids": ["..."],
            "timestamp": "2026-04-10T...",
            "status": "open/sold/won/lost/merged_into_primary",
            "sells": [...],
            "dedup_history": [...]
        }
    },
    "stats": {
        "total_bets": 0,
        "wins": 0,
        "losses": 0,
        "sells": 0,
        "total_pnl": 0.0,
        "peak_balance": 2000.0,
        "current_balance": 2000.0
    }
}
```

### Источник баланса

| Приоритет | Источник | TTL кэша |
|----------|--------|-----------|
| Основной | Баланс USDC в блокчейне (Polygon) | 30 секунд |
| Запасной | Внутренний счётчик `current_balance` | -- |

`get_available_balance()` = `max(0, onchain_balance - RESERVE_USD)`. Резерв = $150 в режиме live.

### Запись позиции (`record_position`)

**Всегда агрегирует**, когда существует открытая запись с тем же (condition_id, token_id):
- Добавляет акции и стоимость
- Пересчитывает взвешенный `avg_entry`
- Увеличивает `parts_filled`
- Добавляет `order_id` в список `order_ids`

Перед записью запускает `consolidate_duplicates()` для самовосстановления существующих дубликатов.

### Запись продажи (`record_sell`)

- Уменьшает `size_shares` на `sell_shares`
- Вычисляет `sell_pnl = sell_revenue - (sell_shares * avg_entry)`
- Добавляет в список `sells[]`
- Обновляет статистику: `sells`, `total_pnl`, `current_balance`
- Если `size_shares < 0.1` после продажи --> status = "sold", вычисляет `final_pnl`

### Консолидация дубликатов (`consolidate_duplicates`)

Группирует открытые позиции по (condition_id, token_id). Если >1 записи в группе:
- Самая старая запись становится основной
- Суммируются все size/cost, пересчитывается avg_entry
- Объединяются списки order_ids и sells
- Остальные помечаются как `status = "merged_into_primary"`
- История объединения записывается в `dedup_history[]`

### Синхронизация с блокчейном (`sync_with_onchain`)

Запускается каждые ~5 минут из `periodic_checks`. Для каждой открытой позиции:
- Получить реальное количество акций из data-api
- **Блокчейн > трекер**: скорректировать вверх (оценить стоимость по avg_entry), записать в `manual_additions`
- **Блокчейн < трекер**: скорректировать вниз, записать в `sells` с причиной `onchain_sync_down`
- **Блокчейн = 0**: пометить как `sold` с причиной `onchain_sync_disappeared`
- Допуск: |разница| < 0.5 акций = игнорировать

### Проверка просадки (`check_drawdown`)

```
total_value = (USDC в блокчейне или внутренний баланс) + sum(cost_usd открытых позиций)
drawdown = (peak_balance - total_value) / peak_balance
```

| Параметр | Значение |
|-----------|-------|
| MAX_DRAWDOWN_PCT | 0.80 (80%) |
| BANKROLL | $2,000 |

Пик динамически обновляется вверх. Если просадка >= 80% --> блокировка новых входов.

### Лимиты

| Параметр | Значение |
|-----------|-------|
| MAX_CONCURRENT | 40 позиций |
| MAX_PER_EVENT | 1 (обеспечивается через `has_position_on_condition`) |

## 14. Механизмы защиты

### 14.1 Защита от фантомных продаж

**Где:** `monitor.py` (сравнение снимков), `exit_manager.py` (handle_player_sell)

**Проблема:** У Denizz 450+ позиций. Пагинация data-api Polymarket нестабильна и иногда выбрасывает позиции из ответа, создавая впечатление их продажи.

**Решение (два уровня):**

1. **Уровень монитора**: Перед запуском on_sell из сравнения снимков, проверить баланс игрока в блокчейне через `CTF.balanceOf`:
   - Если баланс в блокчейне > 5% от предыдущего размера --> ФАНТОМ, пропустить
   - Если RPC не ответил --> защитная мера, пропустить (НЕ продавать)

2. **Уровень менеджера выхода**: Все решения о продаже используют данные блокчейна:
   - `actual_sold = cached_balance - current_onchain_balance`
   - Если actual_sold <= 0 --> ФАНТОМ, пропустить
   - Если RPC не ответил --> защитная мера, пропустить

### 14.2 Правило C: Защита от вертушки после выхода

**Где:** `main.py` -- `handle_buy()`, `_recent_exit_on_market()`

**Проблема:** После выхода из позиции игрок может повторно войти по почти той же цене (флиппинг). Это создаёт вертушку, при которой мы покупаем-продаём-покупаем в быстрой последовательности по схожим ценам, теряя на проскальзывании каждый раз.

**Решение:**
- Сканировать трекер на автоматические продажи по (cid, token) за последние `POST_EXIT_WINDOW_HOURS = 12` часов
- Если найдено и `abs(new_entry_price - exit_price) / exit_price < POST_EXIT_PRICE_CHANGE_MIN = 0.05` (5%) --> ЗАБЛОКИРОВАТЬ повторный вход

**Вариант A:** Ручные выходы (причина начинается с "manual_" или `manual_exit=True`) НЕ учитываются для вертушки. Решения человека не связаны с флиппингом игрока.

**Вариант D:** Порог ужесточён с 10% до 5% (2026-04-09). 10% было слишком широко, блокируя легитимные сигналы повторного набора позиции.

### 14.3 Дедупликация: защита от дублирования событий продажи

**Где:** `exit_manager.py` -- `_recent_exit_fires`

```python
_recent_exit_fires = {}   # {(player, cid, token): last_ts_unix}
EXIT_DEDUP_WINDOW_SEC = 60
```

Если то же событие продажи (player, cid, token) срабатывает в течение 60 секунд --> пропуск дубликата. Merge-события обходят эту защиту.

### 14.4 Консолидация дубликатов в трекере

**Где:** `tracker.py` -- `consolidate_duplicates()`

**Проблема:** Множественные события BUY от одного игрока на одном рынке создавали множество записей в трекере (каждый вызов `record_position` с part=1 создавал новую запись).

**Исправление:** `consolidate_duplicates()` запускается перед каждым `record_position` и в начале `check_exits`. Группирует открытые позиции по (cid, token), объединяет дубликаты в самую старую запись.

### 14.5 Автоматическое прекращение при просадке

**Где:** `tracker.py` -- `check_drawdown()`, `can_open_new()`

Если `(peak_balance - total_value) / peak_balance >= MAX_DRAWDOWN_PCT (0.80)` --> блокировка ВСЕХ новых входов. Пик динамически обновляется вверх по мере роста портфеля.

### 14.6 Обнаружение подготовки к merge (ОТКЛЮЧЕНО)

**Где:** `filters.py` -- `detect_merge_prep()` (существует, но не вызывается)

Было разработано для обнаружения покупок акций игроком для merge (арбитража), а не как направленного сигнала. Отключено после бэктеста, показавшего катастрофическую точность (~1-3%): блокировало ~30% покупок, но <5% были реальными merge.

Смягчение для ложных merge-входов: когда происходит реальный merge, `handle_merge()` в main.py уже выходит из позиции.

### 14.7 Баланс в блокчейне как единственный источник правды

**Где:** `tracker.py` -- `get_available_balance()`, `sync_with_onchain()`

- Доступный баланс для новых ставок считывается из USDC в блокчейне (кэш 30с), НЕ из внутреннего счётчика
- `sync_with_onchain()` запускается каждые ~5 минут: сравнивает акции в трекере с data-api, корректирует вверх/вниз/помечает как проданные

### 14.8 Изоляция по игроку-источнику сигнала

**Где:** `exit_manager.py` -- `handle_player_sell()`

Событие продажи от игрока X запускает выход только для позиций, где `signal_player == X`. Это предотвращает перекрёстное влияние между игроками (например, продажа Car не закроет позицию denizz).

### 14.9 Очистка устаревших сигналов

**Где:** `main.py` -- `_rehydrate_from_tracker()`, направление 2

Каждые ~5 минут удаляются записи `_signaled_keys` для позиций, которые больше не открыты. Без этого устаревшие записи от прошлых позиций блокировали бы новые легитимные сигналы на том же рынке при повторном входе игрока.

### 14.10 Сброс буфера после ручной продажи

**Где:** `tracker.py` -- `reset_buffer_after_manual_sell()`

Утилита для скриптов ручной продажи. Очищает `notified=True` и `last_tier_bet` для (cid, token) в `buy_buffers.json`, чтобы бот не пропустил следующий сигнал на этом рынке.

### Погашение (redeemer.py)

Работает в фоновом потоке. Каждые 300 секунд:
1. Для каждой открытой позиции проверить, разрешён ли рынок в блокчейне (`payoutDenominator > 0`)
2. Для neg_risk рынков также проверить финализацию NegRiskAdapter
3. Если разрешён и мы удерживаем токены: отправить транзакцию `redeemPositions` (до 3 попыток с увеличением газа)
4. Проверить баланс USDC до/после, чтобы определить выигрыш
5. Обновить трекер: `resolve_position(won=True/False)`
6. Уведомить через Telegram: выигрыш (с P&L) или проигрыш (со стоимостью)
