## Детальный разбор

### CRIT-1: Revenue/cost по limit-цене — СОГЛАСЕН

**Проверено:** executor.py:61 (`cost_usd: shares * price`), executor.py:126 (`revenue_usd: shares * price`), entry_manager.py:145 (`actual_cost = size_matched * order_price`), exit_manager.py:566,580 (`revenue = shares * price`).

Везде используется лимитная цена. `wait_for_fill_with_details` НЕ возвращает фактическую цену исполнения — API CLOB отдаёт только `order.price` (лимит).

**Моё мнение:** Проблема реальная, но **масштаб преувеличен**. На Polymarket CLOB лимит-ордер чаще всего исполняется ТОЧНО по лимитной цене (мы ставим на best bid/ask). Разница возникает только когда в стакане есть встречный ордер по лучшей цене. На практике это 1-3 цента на сделку. НО за 400+ позиций это может накопиться в сотни долларов расхождения.

**Риск фикса:** ВЫСОКИЙ. Это рефактор контракта executor → entry_manager → exit_manager → tracker. Нужно:
- Понять отдаёт ли Polymarket API actual fill price (проверить `/trades` endpoint)
- Изменить все цепочки вызовов
- Пересчитать существующие позиции

**Рекомендация:** Делать ПОСЛЕДНИМ, после всех остальных фиксов. Сначала собрать данные из A/B теста (limit_ab_log.csv уже копит данные о реальных ценах).

### CRIT-2: resolve_position — СОГЛАСЕН, ЧИНИТЬ ПЕРВЫМ

**Проверено 3 бага:**

1. **Строка 520:** `stats["current_balance"] += pos["size_shares"] + (pos["size_shares"] if won else 0)` — при win прибавляет 2x shares. Должно быть: `+= payout` (= size_shares для won), `+= 0` для lost.

2. **Строка 514:** `net_new_pnl = pnl` в ветке lost — не вычитает `already_counted`. Если мы частично продали с PnL +$20, а потом позиция проиграла — total_pnl посчитает полный убыток БЕЗ учёта уже записанного +$20.

3. **Строка 518:** `pos["final_pnl"] = pnl + sum(sells.pnl)` — в ветке won двойной учёт partial sells.

**Риск фикса:** НИЗКИЙ. Функция вызывается только при резолюции рынка. Не влияет на торговую логику (вход/выход). Влияет только на отчётность и kill switch.

**Можно ли положить бота:** НЕТ. Фикс меняет только расчёт баланса при закрытии позиции.

---

### CRIT-3: Redeem nonce — СОГЛАСЕН, но ПРИОРИТЕТ НИЖЕ

**Проверено:** redeemer.py:178 — каждый attempt делает свежий `get_transaction_count('pending')`. Между реедемами sleep(5), что может быть меньше времени подтверждения блока.

**Моё мнение:** Проблема реальная, но:
- Деньги НЕ теряются — реедем просто откладывается до следующего цикла
- Газ на Polygon почти бесплатный
- Проблема проявляется только при массовом реедеме (много позиций резолвятся одновременно)

**Простой фикс:** увеличить sleep между реедемами с 5 до 15 секунд. Nonce manager — хорошо, но overkill для нашего объёма.

### HIGH-1: Retry-цена на дешёвых токенах — СОГЛАСЕН

**Проверено:** `round(0.05 * 0.98, 2) = 0.05` — цена не двигается. Retry бесполезен.

**Фикс:** 3 строки, нулевой риск.

---

### HIGH-2: consecutive_errors — СОГЛАСЕН

**Проверено:** `getattr(e, '_consecutive', 0)` всегда возвращает 0. Backoff всегда = POLL_INTERVAL * 2.

**Фикс:** 1 строка (`consecutive_errors += 1`), нулевой риск.

---

### HIGH-3: seen_keys — СОГЛАСЕН, но LOW приоритет

Бот перезапускается регулярно (при деплое фиксов), поэтому утечка памяти не критична. За день работы ~1000 ключей, это ничтожно.

**Фикс:** можно сделать, но не срочно.

---

### HIGH-4: sync_with_onchain N+1 — НЕ СОГЛАСЕН

**Проверено:** Код делает ОДИН bulk fetch всех позиций (строки 599-622), сохраняет в dict, потом ищет по ключу. N+1 запросов НЕТ. Opus 4.7 ошибся — возможно смотрел на старую версию кода или на другой бот (25_multi_signal_copybot без _v2).

---

### HIGH-5: Пустой стакан (0.0, 1.0) — ЧАСТИЧНО СОГЛАСЕН

**Проверено:** `get_orderbook_prices` действительно возвращает `(0.0, 1.0)` при пустом стакане. Стоп-лосс теоретически сработает (drop_pct = 1.0 >= 0.80). НО: `safe_sell` в executor не даст продать по 0.0 (min price check).

**Риск:** Низкий реально, но стоит добавить `return None` при пустом стакане для чистоты.

---

### HIGH-6, HIGH-7: Thread safety + div/0 — СОГЛАСЕН, LOW приоритет

Оба теоретические. На практике client создаётся до первого сигнала, а price=0 фильтруется в мониторе. Но defence-in-depth — хорошая практика. 5 строк каждый.

---

### HIGH-8: Мёртвый код check_hedge_exits — СОГЛАСЕН

Удалить. 0 риска.

---

### HIGH-9: TG блокирует монитор — СОГЛАСЕН

**Проверено:** `tg.player_buy` — синхронный HTTP. При таймауте Telegram (10-30с) задержит обработку следующего BUY.

**Фикс:** обернуть в daemon thread. 3 строки. Низкий риск.

## ИТОГ

Из 3 критических находок Opus 4.7 — **все 3 подтверждены**. Из 9 HIGH — **1 ошибка** (HIGH-4 не существует), остальные подтверждены.

Качество ревью: **высокое**. Opus 4.7 нашёл реальные баги, особенно CRIT-2 (resolve_position) — это баг который напрямую портит отчётность.

**Главный вывод:** бот ТОРГУЕТ правильно (входы/выходы по правильным ценам на основе on-chain данных), но СЧИТАЕТ PnL неточно. Это значит реальные деньги не теряются из-за этих багов, но отчёты и kill switch ненадёжны.
