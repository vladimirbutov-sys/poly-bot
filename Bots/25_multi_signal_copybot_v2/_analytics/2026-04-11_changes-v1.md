## Изменение 3: Горизонт по дате окончания рынка (End-date horizon)

### AS IS

**filters.py** (строки 685-713):

```python
LONG_HORIZON_CUTOFF = datetime(2026, 12, 1, tzinfo=timezone.utc)
LONG_HORIZON_MULTIPLIER = 0.2
```

Логика:
- Если `end_date >= 2026-12-01` -- множитель 0.2 (ставка уменьшается в 5 раз)
- Если `end_date < 2026-12-01` -- множитель 1.0 (без изменений)
- Бинарное решение: или 100%, или 20%. Промежуточных значений нет
- Привязана к фиксированной дате (1 декабря 2026), а не к расстоянию до конца

Функции:
- `is_long_horizon(end_date_str)` (строка 689) -- возвращает True/False
- `get_long_horizon_multiplier(market_info)` (строка 701) -- возвращает (множитель, причина)

Вызовы:
- `filters.py` строка 625 -- при расчете ставки: `lh_mult, lh_reason = get_long_horizon_multiplier(market_info)`
- `main.py` строка 432 -- при top-up: `lh_mult, lh_reason = filters.get_long_horizon_multiplier(_mi)`

### TO BE

**Градуированная система** -- множитель зависит от количества дней от момента ставки до end_date рынка:

| Дней до end_date | Множитель | Логика |
|---|---|---|
| 0-30 дней | 1.0 | Короткий горизонт — полная ставка |
| 30-60 дней | 0.8 | Средний горизонт — небольшое снижение |
| 60-90 дней | 0.7 | Длинный горизонт — умеренное снижение |
| 90-120 дней | 0.4 | Очень длинный — значительное снижение |
| 120+ дней | **БЛОКИРОВКА** | **Не входим.** Капитал замораживается слишком надолго |

Правила применения:
- Считается от **момента размещения ставки**, не от ребалансировки
- При **top-up** (доливке) -- пересчитывается на основе текущего расстояния до end_date
- Множитель применяется один раз при входе

Новая функция:
```python
def get_horizon_multiplier(end_date_str) -> tuple:
    """Градуированный множитель по расстоянию до end_date.
    120+ дней = БЛОКИРОВКА (возвращает 0.0).
    90-120 дней = 0.4.
    
    Возвращает (multiplier, reason).
    """
```

Удалить:

- `LONG_HORIZON_MULTIPLIER` (константа)
- `is_long_horizon()` (функция)
- `get_long_horizon_multiplier()` (функция)

## Изменение 4: Расширенный follow-sell (следование за продажами Denizz)

### AS IS

**Файл:** `exit_manager.py`

Бот реагирует на продажи Denizz только в двух случаях:
- Denizz продал **≥ 70%** позиции → продаём **100%** (rule 3: big dump)
- Denizz продал **100%** / merge → продаём **100%**
- Продажи < 70% → **игнорируются полностью**

```
sell_ratio = проданные_шары / общее_шар_до_продажи

sell_ratio < 70%  → НЕ РЕАГИРУЕМ
sell_ratio >= 70% → ПРОДАЁМ 100%
```

### TO BE

Градуированная система выхода, зависящая от sell_ratio И нашего PnL:

| Denizz sell_ratio | Мы в прибыли (PnL > 0) | Мы в убытке (PnL < 0) |
|---|---|---|
| < 10% | **Не выходим** (ребалансирование) | **Не выходим** |
| 10-30% | Продаём **25%** | **Не выходим** (ждём восстановление) |
| 30-60% | Продаём **50%** | **Не выходим** (ждём стоп-лосс) |
| 60-90% | Продаём **75%** | Продаём **75%** (Denizz серьёзно уходит) |
| > 90% | Продаём **100%** | Продаём **100%** |

**Логика для убыточных позиций — кумулятивный sell_ratio:**

При PnL < 0 используется **кумулятивный** sell_ratio вместо разового:

```
cumulative_sell_ratio = (peak_player_size - current_player_size) / peak_player_size
```

Где `peak_player_size` — максимальный размер позиции Denizz, который мы запоминаем в трекере.

| | В прибыли (PnL > 0) | В убытке (PnL < 0) |
|---|---|---|
| **Какой sell_ratio** | **Разовый** (этой продажи) | **Кумулятивный** (от пика) |
| < 60% | Таблица выше (25%/50%) | **Не выходим** |
| ≥ 60% | Таблица выше (75%/100%) | **Выходим** (75%/100%) |

**Пример серийного выхода Denizz при нашем убытке:**

| Шаг | Denizz продал | Осталось | Разовый | Кумулятивный | Наше действие |
|---|---|---|---|---|---|
| 1 | 200 из 1000 | 800 | 20% | 20% | Не выходим |
| 2 | 200 из 800 | 600 | 25% | 40% | Не выходим |
| 3 | 200 из 600 | 400 | 33% | **60%** | **Продаём 75%** |
| 4 | 200 из 400 | 200 | 50% | 80% | Продаём 100% |

Без кумулятивного — мы бы не вышли до шага 5 (последний). С кумулятивным — вышли на шаге 3.

### Что менять

| Файл | Изменение |
|---|---|
| `exit_manager.py` | Заменить бинарную проверку (≥70% → 100%) на градуированную таблицу. Для PnL < 0: использовать кумулятивный sell_ratio от peak |
| `tracker.py` | Хранить `peak_player_size` для каждой открытой позиции |

## Изменение 4a: Тиерованный стоп-лосс (исправление по аудиту CRITICAL-1)

### AS IS

Единый стоп-лосс: -65% от цены входа для всех позиций.
HP-позиции (95-99c): отдельный стоп при bid <= 80c.

Пример: вход по 96c → стандартный стоп = 96 × 0.35 = 33.6c (потеря 65%). HP стоп = 80c (потеря 17%).

### TO BE

## Изменение 10: Модификация Rule C (whipsaw protection)

### AS IS

**Файл:** `main.py`, строки 225-481

Rule C блокирует перевход в позицию если **оба** условия выполнены:

```

2. |new_entry_price - our_exit_price| / our_exit_price < 5%
```

Блокировка применяется **безусловно** — неважно, вышли мы с прибылью или убытком.

**Параметры:**
- `POST_EXIT_WINDOW_HOURS = 12`
- `POST_EXIT_PRICE_CHANGE_MIN = 0.05` (5%)

### TO BE

Добавляем **третье условие** — проверку PnL предыдущей сделки:

```
Rule C блокирует если:
1. Прошло < 12 часов с последней автоматической продажи
2. |new_entry_price - our_exit_price| / our_exit_price < 5%
3. PnL последнего sell на этом (condition_id, token_id) <= 0    ← НОВОЕ
```

Если предыдущая сделка была **прибыльной** (PnL > 0) → Rule C **не применяется**, перевход разрешён.

| Предыдущий выход | Цена изменилась < 5% | Rule C AS IS | Rule C TO BE |

| Убыток (PnL ≤ 0) | Да | **БЛОК** | **БЛОК** |
| Убыток (PnL ≤ 0) | Нет (≥ 5%) | Разрешён | Разрешён |
| **Прибыль (PnL > 0)** | **Да** | **БЛОК** | **Разрешён** ← изменение |
| Прибыль (PnL > 0) | Нет (≥ 5%) | Разрешён | Разрешён |

## Изменение 11 (было 9): Плавная формула размера ставки

### AS IS

4 фиксированных ступени по сумме покупок Denizz за 24ч:

| Denizz купил за 24ч | Наша ставка |
|---|---|
| < $500 | skip |
| $500+ | $30 |

| $5,000+ | $105 (+$50) |
| $10,000+ | $200 (+$95) |

**Проблема:** резкие скачки. $4,999 → $55, $5,001 → $105. Разница $2 у Denizz = разница $50 у нас.

### TO BE

Логарифмическая формула без скачков:

```
our_bet = 31.75 × ln(denizz_buy_24h) − 177
```

Порядок расчёта:
```
Шаг 1: raw_bet = min(150, 31.75 × ln(invested) − 177)    # формула с cap $150
Шаг 2: raw_bet = raw_bet × множитель_цены × множитель_горизонта
```

- Максимум **$150** за один вход — проверяется **до** множителей (cap формулы)
- Максимум **$200** суммарно в одной позиции (10% банкролла)

**Что значит формула простыми словами:**

- $500 (минимальный порог) → $20 (минимальная ставка)
- $30,000 (практический максимум Denizz за 24ч) → $150 (потолок ставки)
